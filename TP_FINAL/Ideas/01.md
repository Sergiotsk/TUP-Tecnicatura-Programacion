# Propuesta 01 — Hub Operativo para Anfitriones de Alquiler Temporario (con IA)

**Estado:** en construcción — para presentar al grupo antes del viernes de definición con la profesora
**Autor:** Sergio (Sergiotsk) · Estudiante TUP
**Fecha:** agosto 2026

---

## 1. Problema

Los anfitriones que administran entre 2 y 10 departamentos de alquiler temporario (Airbnb, Booking, etc.) pierden tiempo y plata en tareas operativas que hoy se hacen a mano:

- Coordinar limpieza entre el check-out de un huésped y el check-in del siguiente, sin choques de agenda.
- Fijar el precio por noche "a ojo", sin datos de estacionalidad ni ocupación histórica — dejando plata sobre la mesa o perdiendo reservas por sobreprecio.
- Responder siempre las mismas preguntas de huéspedes (wifi, horarios, reglas de la casa) de forma manual.
- Mantener sincronizados los calendarios de varias plataformas para no dar el mismo departamento dos veces.

## 2. Solución — MVP

Plataforma web para anfitriones que centraliza:

1. **Sincronización de calendarios** vía iCal (Airbnb, Booking) en una agenda unificada.
2. **Módulo de limpieza/mantenimiento**: asigna tareas automáticas al personal de limpieza al detectar un check-out, con checklist de fotos del estado del departamento.
3. **Portal del huésped**: link único autogenerado por reserva, con clave de wifi, reglas de la casa, y un **chat web embebido** para consultas (ver sección de decisión de canal).
4. **Motor de pricing dinámico**: sugiere precio por noche según estacionalidad, día de la semana y ocupación histórica del anfitrión.

### Diferenciador de IA (el corazón académico de la propuesta)

- **Pricing dinámico basado en datos**: modelo estadístico (no ML pesado) que pondera estacionalidad + día de semana + tasa de ocupación histórica para sugerir precio óptimo.
- **Asistente conversacional para huéspedes**: máquina de estados (FSM) + fallback con LLM (OpenAI/Claude) para consultas libres, corriendo sobre el chat web del portal del huésped.

## 3. Decisión de arquitectura: canal de chat (por qué NO WhatsApp en el MVP)

Evaluamos usar la API de WhatsApp Business (Meta) para el chat de huéspedes, pero se descarta **para el MVP** por evidencia concreta de fricción real (verificación de negocio, Embedded Signup con race conditions, tokens que rotan, aprobación de templates) documentada en un proyecto propio anterior que integró esa misma API. Ese costo de tiempo no aporta valor al problema que se está resolviendo (gestión de propiedades), solo agrega dependencia de aprobación de un tercero fuera de nuestro control.

**Decisión**: separar el **core de conversación** (FSM + fallback IA) del **canal de entrega**, siguiendo el patrón de puertos y adaptadores (arquitectura hexagonal):

- **Adaptador Web Chat (MVP)**: chat en tiempo real embebido en el portal del huésped, vía Supabase Realtime. El huésped entra por el link único de su reserva, sin necesidad de login ni número de teléfono.
- **Adaptador WhatsApp (roadmap futuro)**: se agrega como un adaptador nuevo cuando el producto lo justifique, sin tocar el core de conversación.

Esta decisión es también un argumento de diseño defendible en la presentación: demuestra separación de responsabilidades y bajo acoplamiento entre lógica de negocio y canal de entrega.

## 4. Stack tecnológico

| Capa | Tecnología | Por qué |
|------|-----------|---------|
| Dashboard anfitrión | Next.js + React + TypeScript + Tailwind + Radix UI | Stack ya dominado por el equipo (base común con otros proyectos propios) |
| API / Bot / Jobs | **NestJS** (Node.js + TypeScript) | Arquitectura modular con inyección de dependencias — da consistencia en equipo de niveles mixtos y es defendible como Clean Architecture |
| Base de datos | Supabase (Postgres + RLS) | Multi-tenant real: cada anfitrión ve solo sus propiedades |
| Storage de fotos | Supabase Storage | Ya integrado, sin sumar proveedores externos innecesarios |
| Sync de calendarios | `ical.js` + cron job (`@nestjs/schedule`) | Estándar de la industria para iCal, sin reinventar |
| Canal de chat (MVP) | Supabase Realtime (chat web embebido) | Evita dependencia de aprobación de Meta para el MVP |
| Canal de chat (futuro) | Adaptador WhatsApp Business API | Se agrega post-MVP sin tocar el core |
| Pricing dinámico | Modelo estadístico simple (estacionalidad + ocupación histórica) | Defendible a nivel TUP, sin comprometerse a ML pesado en el MVP |
| Fallback conversacional | OpenAI/Claude API | Manejo de preguntas libres del huésped |
| Pagos (si entra en el MVP) | Mercado Pago | Evaluar si entra en alcance o queda para roadmap |
| Deploy | Vercel (web) + Railway (API/bot) | Infraestructura conocida por el equipo |
| Monorepo | pnpm workspaces (`apps/web`, `apps/api`, `packages/types`) | Tipos compartidos entre frontend y backend |

## 5. Aspectos de compliance a diseñar desde el inicio

- La foto de DNI del huésped (registro/check-in) es un dato personal sensible → requiere cifrado en reposo y política de retención clara (Ley 25.326, Argentina). Se incluye en el diseño desde el MVP, no como parche posterior.

## 6. Roadmap a futuro (visión de producto, fuera del alcance del MVP)

- Extensión del modelo de datos (ya genérico desde el diseño) a **alquiler tradicional/inmobiliarias**, agregando un módulo de scoring de riesgo de inquilino — **sin mezclarlo en el MVP** para no diluir la profundidad del proyecto de tesis.
- Adaptador de canal WhatsApp para el chat de huéspedes.
- Detección de daños por visión artificial, comparando fotos del checklist de limpieza antes/después.
- Monetización real: suscripción mensual por departamento administrado (referencia de mercado: entre USD 5 y 10/depto/mes).

## 7. División de tareas sugerida (equipo de niveles mixtos)

| Nivel | Módulo sugerido |
|-------|------------------|
| Junior | CRUD de propiedades, formularios, portal del huésped (UI) |
| Mid | Sincronización iCal, módulo de limpieza/checklist, chat en tiempo real |
| Senior | Motor de pricing dinámico, arquitectura NestJS (módulos/DI), diseño del modelo de datos multi-tenant con RLS |

## 8. Riesgos identificados

| Riesgo | Mitigación |
|--------|-----------|
| Curva de aprendizaje de NestJS para integrantes junior | Sesión de estudio grupal de conceptos base (módulos, DI, decoradores) antes de arrancar a codear |
| Compliance de datos personales (foto DNI) | Diseñar cifrado y retención desde el modelo de datos inicial |
| Alcance del MVP se infla mezclando alquiler temporario + tradicional | Mantener el MVP enfocado en alquiler temporario; la extensión queda solo como roadmap documentado |

## 9. Por qué esta propuesta frente a las otras del grupo

Comparada con las otras ideas presentadas por el grupo (comparador de precios mayoristas, extractor de gastos con OCR, optimizador de merma, hub Airbnb sin IA), esta versión combina:

- Complejidad técnica real y defendible (pricing dinámico con datos, arquitectura hexagonal, multi-tenant).
- Bajo riesgo de bloqueo externo (se evita la dependencia de aprobación de Meta en el MVP).
- Potencial de continuidad como producto real: el nicho de anfitriones está más organizado y con mayor poder de compra que otros nichos evaluados (comercios chicos, por ejemplo).

## 10. Flujo de trabajo en equipo (Git + monorepo)

Se confirma **monorepo con pnpm workspaces** (no repos separados por app) por tres motivos concretos para un equipo de niveles mixtos:

- Tipos compartidos (`packages/types`) entre `apps/web` y `apps/api`: un cambio de contrato rompe el build al instante para todos los que dependen de él, en vez de descubrirse tarde.
- Un solo `git clone` + `pnpm install` para todo el equipo — menos fricción de setup para los integrantes con menos experiencia en tooling.
- Code review con contexto completo: un PR que toca API y frontend a la vez se revisa junto.

**Convenciones para evitar que el equipo se pise entre sí:**

- Ramas por módulo/feature, alineadas a la carpeta que tocan: `feat/pricing-engine`, `feat/chat-widget`, `feat/ical-sync`.
- PRs chicos y frecuentes en vez de branches largos — más fácil de revisar entre compañeros de niveles distintos.
- Opcional (evaluar si el equipo crece en tareas paralelas): Turborepo para que el CI solo corra sobre los paquetes que cambiaron. No es requisito para el alcance de este TP.
